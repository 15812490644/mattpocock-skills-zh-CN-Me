# Mailbox 契约

`mailbox/` 目录的文件协议，唯一权威。`SKILL.md` 与 `subagent-prompt.md` 都指向这里，规则只在此维护。

两条铁律：

1. **一个文件一个写入者**——每个文件只有唯一角色能写，其余角色只读。写入者见下表，没有例外。
2. **只加不改**——日志类文件只追加，从不修改或删除旧内容；同一 id 出现多行时，以最后一行为准。

两个边界：用户 ↔ 通讯官 走 chat 对（经监控脚本桥接聊天室）；通讯官 ↔ 主 agent 走 mailbox 对。`status.md` 全员可读，只有主 agent 写。

| 文件 | 写入者（唯一） | 读者 | 内容 |
|------|----|----|------|
| `chat-in.md` | 监控脚本（追加） | 通讯官 | 用户在聊天室的原话 |
| `chat-out.md` | 通讯官（追加） | 监控脚本 → 聊天室 | 通讯官给用户的大白话消息 |
| `inbox.md` | 通讯官（追加卡片） | 主 agent（缝隙查收） | 用户确认过的消息卡片 |
| `inbox-status.md` | 主 agent（追加） | 通讯官、用户 | 卡片处理结果，一行一个 id |
| `outbox.md` | 主 agent（追加条目） | 通讯官 | 问题、阻塞、需决策事项 |
| `outbox-replies.md` | 通讯官（追加） | 主 agent（缝隙查收） | 用户答复，一行一个 id |
| `status.md` | 主 agent（覆盖更新） | 通讯官、用户、监控脚本 | 当前任务 / 阶段 / 阻塞 / DONE |

`status.md` 是唯一的例外：它由主 agent 覆盖式更新——单一写入者，且全员只读它，不存在追加冲突。

## 消息卡片（inbox.md）

通讯官追加到 `inbox.md` 的唯一格式：

```markdown
## [MSG-001]
- 类型: 要求 | 反馈 | 建议 | 疑似bug | STOP
- 优先级: 高 | 中 | 低
- 用户原话: "……"
- 整理后: ……（通讯官用技术语言重述，补全必要上下文）
- 投递时机: 下一缝隙 | 攒批
```

- id 递增（MSG-001、MSG-002……），不复用。
- 卡片落盘即视为已确认、已投递，不再单独标注状态。
- 主 agent 处理完，在 `inbox-status.md` 追加一行：`- MSG-001 | 已处理 | <一句话处理结果>`。卡片本身永远保持原样。

## 四类 + STOP

- **要求** —— 用户说必须做的。主 agent 下一缝隙收到后优先处理；与当前方向冲突时，经 outbox 与用户确认再动。
- **反馈** —— 对已交付部分的评价。攒批到阶段边界吸收。
- **建议** —— 可选优化。攒批到阶段边界吸收；主 agent 也可在边界主动问"有建议吗"。
- **疑似bug** —— 用户观察到的是症状不是结论。卡片必须带三样：观察到的现象、操作步骤、期望结果。主 agent 复现验证后才按真 bug 处理；复现不了，把缺失信息写进 `outbox.md` 请通讯官补齐。
- **STOP** —— 用户说"停"。最高优先，当前原子操作完成后立即暂停。

用户可随时一句话覆盖分类（"这条是必须"），通讯官据此改写卡片类型。

## 投递时机

| 卡片 | 时机 |
|------|------|
| 要求、高优先级疑似bug、STOP | 下一缝隙 |
| 反馈 | 攒批，阶段边界 |
| 建议 | 攒批，阶段边界或主 agent 主动问时 |

缝隙 = 主 agent 完成一个原子任务之后、开始下一个之前。原子任务中途不收件。

## outbox.md 条目

```markdown
## [ASK-001]
- 问题: ……（主 agent 的技术表述）
- 需要用户回答: ……
```

通讯官翻译成大白话经 chat-out 问用户，拿到回答后在 `outbox-replies.md` 追加一行：`- ASK-001 | 已答复 | <用户答复>`。主 agent 在缝隙查收答复。

## status.md

主 agent 覆盖式更新：

```markdown
# 状态
- 当前: 正在做什么（一句话）
- 阶段: flow 路线上的位置
- 阻塞: 无 | ……
- 更新于: <时间>
```

任务完成时写 `DONE`（单独一行）。监控脚本发现 DONE 后唤醒通讯官：向用户发最终总结，然后自行退出。闲置兜底规则见 `subagent-prompt.md`——连续 30 分钟无唤醒且无未闭环事项才退出。

## 监控脚本契约（chat-watcher.py）

占位文件，由用户的真实实现替换。它是唯一常驻的进程，职责四件：

1. **搬运进**：聊天室里的用户新消息 → 原样追加到 `chat-in.md`（每条一段，带时间戳）。
2. **即时回**：检测到 `chat-in.md` 新消息后，立刻往聊天室发一条自动应答（"收到，马上转给开发主力"），让用户知道已被看到——直接发到聊天室，不写 `chat-out.md`（保持它只有通讯官一个写入者）；实质答复由通讯官随后补上。
3. **唤醒**：检测到 `chat-in.md`、`outbox.md` 有新增，或 `status.md` 有变化 → 按宿主机制唤醒通讯官。通讯官不轮询，一切由脚本叫醒。
4. **搬运出**：`chat-out.md` 的新增内容 → 推送到聊天室展示。

语言不限，事件驱动优先，轮询兜底间隔几秒即可。它只做搬运、即时应答和叫醒——分类、翻译、确认都是通讯官的工作。
