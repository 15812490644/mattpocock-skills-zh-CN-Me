

# Liaison 聊天室实施计划书

> **本文档的读者是下一个负责实施的 AI**（下称"实施者"），不是最终用户。
> 目标：把 liaison-v2 技能中两个占位空文件 `chatroom.html` 与 `chat-watcher.py` 实现为可用成品。
> 前置约束：**最终用户不会编程，只用成品**。所有部署、启动、排障均由 AI 完成；用户唯一的动作是"打开一个网页、输入地址和房间号、开始聊天"。

---

## 1. 背景与使用场景

### 1.1 这是什么

liaison-v2（通讯官）技能为长时间自动化任务建立"用户 ↔ 通讯官子 agent ↔ 主 agent"的三方通信结构（完整契约见 liaison 技能的 `mailbox-format.md`，本文不复述，**它是文件协议的唯一权威**）。其中两个文件是占位空壳，需要实现：

| 文件 | 角色 | 类比 |
|---|---|---|
| `chatroom.html` | 用户面对的聊天界面 | 用户家里的"对讲机" |
| `chat-watcher.py` | 常驻进程，桥接聊天室与 mailbox，并叫醒通讯官 | 小区门口的"传达室大爷" |

### 1.2 使用场景（功能必须适配这些场景）

- **用户画像**：不会编程的个人用户，让 AI 做耗时较长的成品（手机 app、HTML 小网页、游戏 mod 等）。
- **设备**：用户在自己**日常使用的电脑和手机浏览器**上打开聊天室；**与 AI 的运行环境通常不是同一台机器**，通过网络连接。
- **典型一天**：用户让 AI 开工一个大任务 → AI 启动 watcher 并告诉用户"地址 + 房间号" → 用户在手机浏览器打开聊天室网页 → 做饭、出门，期间偶尔看一眼：通讯官用大白话汇报进展、AI 有问题就醒目地等用户回答 → 用户随时按"停！"让 AI 暂停 → 任务结束，通讯官发来大白话总结。
- **多项目**：用户可能先后（或并行）有多个任务，每个任务一个房间号，可切换。

### 1.3 已敲定的产品决策（ grilling 结论，不要擅自推翻 ）

| # | 决策 |
|---|---|
| D1 | 聊天室是**单个独立 HTML 文件**，双击即可在浏览器打开，不依赖任何安装 |
| D2 | **响应式布局**，手机小屏必须好用 |
| D3 | 连接方式：首次输入一次**服务器地址 + 房间号**，之后自动记住（localStorage） |
| D4 | **一个房间号 = 一个任务/项目**；网页记住进过的房间列表，一键切换 |
| D5 | 对话内容：**只显示通讯官发的大白话**，不展示主 agent 的技术细节 |
| D6 | **历史记录自动恢复**：重开网页、换设备都能看到之前的对话（历史存服务端，网页拉取） |
| D7 | **多端同时在线**，消息实时同步 |
| D8 | 功能清单：① 四个快捷按钮「停！」「这条是必须」「报个问题」「我有个建议」；② 待答问题醒目置顶横幅；③ 发图片/截图（手机端即拍照上传） |
| D9 | 提醒方式：只做**网页内提醒**，不做浏览器推送通知 |
| D10 | **不做**常驻进度面板；进展由通讯官以大白话消息形式发进对话流 |

## 2. 术语表（领域模型）

| 术语 | 定义 |
|---|---|
| **mailbox** | AI 工作目录下的 `mailbox/` 目录，一组 markdown 文件，两个 agent 经它异步通信 |
| **房间 (room)** | 一个任务/项目对应的独立通信空间。房间号是用户侧的称呼；技术上是一个房间 id |
| **通讯官 (liaison)** | 拥有独立上下文的子 agent，负责翻译、分类、确认，是唯一对用户"说话"的 agent |
| **主 agent** | 执行开发任务的 agent，只读写 mailbox，不与用户直接对话 |
| **watcher / 哨兵** | `chat-watcher.py`，唯一常驻进程：搬运消息、即时应答、叫醒通讯官、对外提供网络服务 |
| **缝隙** | 主 agent 完成一个原子任务后、开始下一个之前的查收时机 |
| **闭环** | 一条消息从发出到处理完毕的全过程；未闭环事项 = 未确认消息 / 未成卡 bug / 未送达答复 |
| **待答 (pending ask)** | `outbox.md` 中已提问但 `outbox-replies.md` 中尚无对应答复行的条目 |
| **覆盖语** | 用户一句直接改变分类/流程的话（"这条是必须"、"停"） |

## 3. 总体架构

```
用户浏览器(电脑/手机, file:// 打开的独立 chatroom.html)
        │  WebSocket (消息/历史/同步) + HTTP POST (图片)
        ▼
chat-watcher.py  ── 常驻进程，同时是 HTTP/WebSocket 服务器
        │  追加 / 读取 / 监听文件变化
        ▼
mailbox/rooms/<roomId>/   (九文件契约 + images/ 目录)
        ▲
        │  唤醒信号（宿主机制，见 §6.4）
     通讯官子 agent  ←→  主 agent
```

**关键架构事实**：浏览器里的 HTML 无法直接读写本地文件，所以 watcher 必须兼任网络服务器——聊天室的一切数据都经过 watcher 进出 mailbox。watcher 是"唯一会同时碰网络和文件"的组件，职责边界必须清晰：**它只做搬运、即时应答、叫醒和文件服务；分类、翻译、确认永远是通讯官的事**（契约原文要求）。

## 4. `chatroom.html` 规格

### 4.1 硬性技术要求

- **单文件**：全部 HTML/CSS/JS 内联，零外部依赖（不引 CDN——用户网络环境不可控）。
- **file:// 可打开**：双击即运行。因此与 watcher 的通信是跨域的：
  - 消息主通道用 **WebSocket**（不受同源策略限制，天然支持多端实时同步）；
  - 图片上传用 `fetch POST`（需要 watcher 返回 `Access-Control-Allow-Origin: *`）。
- 纯原生 JS，任何 ES2018+ 浏览器可用；布局用 CSS flex，移动端优先（mobile-first），`viewport` 必须设置。
- 界面语言：简体中文。所有文案大白话，禁止出现技术词汇（如 WebSocket、token、端口——叫"地址""房间号"）。

### 4.2 界面结构（自上而下）

1. **顶栏**：当前房间号 + 房间切换按钮（下拉列出历史房间，可"加入新房间"）+ 连接状态指示灯（绿=已连接，红=断线，断线时自动重连并显示"正在重新连接…"）。
2. **待答横幅**（仅在有 pending ask 时出现）：醒目底色置顶，显示 AI 正在等回答的问题，点击即把焦点定位到输入框并插入 `#回答 ASK编号 ` 前缀。多条待答可横向滑动。
3. **消息流**：气泡式对话。左侧=通讯官（大白话），右侧=用户自己。系统提示（如"通讯官已上线"）用居中灰色小字。每条消息带时间。图片消息可点开看大图。
4. **快捷按钮栏**（输入区上方，四个）：
   - 「停！」— 红色，点击二次确认（"确定要暂停手上的活吗？"）后发送覆盖语 `停`；
   - 「这条是必须」— 发送 `这条是必须`（用于纠正分类）；
   - 「报个问题」— 向输入框填入模板：`【看到的现象】\n【我怎么操作的】\n【我本来期待】\n`（对应契约中疑似bug必填三样），引导用户补全；
   - 「我有个建议」— 向输入框插入前缀 `建议：`。
5. **输入区**：多行文本框（自动增高）+ 发送按钮 + 图片按钮（`input[type=file][accept="image/*"]`，手机端自动唤起相册/相机）。

### 4.3 首次连接流程

1. 打开网页 → 若无已存配置，显示连接卡片：两个输入框（"地址"、"房间号"）+ 大字说明"地址和房间号，问给你干活的 AI 要"。
2. 输入后点"进入"→ 建立 WebSocket → 成功则把 `(地址, 房间号, 房间显示名)` 存入 localStorage，之后打开网页自动直连最近的房间。
3. 失败则显示人话错误："连不上。请检查：① 地址房间号有没有抄错；② 问问 AI 是不是还在开工状态。"

### 4.4 历史与多端同步

- 连接成功后，watcher 推送该房间全量历史（来自 `chat-in.md` / `chat-out.md` 的解析结果，见 §5.3），网页渲染后滚到底部。
- 多端：每个连接都订阅同一房间，watcher 对房间内所有连接做广播，天然实现同步。每个客户端生成随机 `clientId` 随消息上报，用于把自己的消息渲染在右侧（不同设备打开同一房间时，凡 user 消息一律右侧即可，无需区分设备）。

## 5. `chat-watcher.py` 规格

### 5.1 硬性技术要求

- **单文件、Python 标准库实现、零 pip 依赖**（沙箱/用户环境可能无法安装包）。Python ≥ 3.8。
- WebSocket 服务端用纯标准库手写极简实现（`socket` + `hashlib/base64` 握手 + 帧编解码，约 100 行，仅支持文本帧与 ping/pong，足够本场景）。若实施者判断维护成本过高，允许退化为 **HTTP 长轮询**（客户端每 2 秒 GET `/poll?since=<id>`），但必须在代码中保留切换开关，默认 WebSocket。
- 启动命令唯一：`python3 chat-watcher.py [--host 0.0.0.0] [--port 8765] [--mailbox <mailbox绝对路径>]`，默认监听 `0.0.0.0:8765`。
- 启动时向 stdout 打印一段给主 agent 的接入信息（监听地址、已有房间列表），并写入 `mailbox/watcher.pid`。

### 5.2 目录结构（多房间）

```
mailbox/
├─ watcher.pid
└─ rooms/
   └─ <roomId>/            # 房间号 = 目录名，4~6 位数字或小写字母，由通讯官/主 agent 开工时创建
      ├─ chat-in.md        # 契约九文件，格式与 liaison mailbox-format.md 完全一致
      ├─ chat-out.md
      ├─ inbox.md
      ├─ inbox-status.md
      ├─ outbox.md
      ├─ outbox-replies.md
      ├─ status.md
      ├─ chatroom.html     # 冗余放一份成品网页，便于主 agent 发给用户（可选）
      └─ images/           # 用户上传的图片，<msgId>.<ext>
```

> 房间九文件的初始模板从 liaison 技能 `files/` 目录复制。契约的写入者规则（一个文件一个写入者、只加不改）**不变**：watcher 只写 `chat-in.md`；`chat-out.md` 仍只有通讯官能写，watcher 只读它并搬运。

### 5.3 网络接口

**WebSocket `/ws?room=<roomId>&client=<clientId>`** —— JSON 文本消息：

| 方向 | type | 载荷 | 说明 |
|---|---|---|---|
| s→c | `history` | `{messages:[{id,from,text,ts,image?}], pending:[{askId,question}]}` | 连接即推送；`from` ∈ `user`/`liaison`/`system`；历史由 `chat-in.md`/`chat-out.md` 按时间戳归并解析 |
| c→s | `chat` | `{text}` | watcher 原样追加到 `chat-in.md`（带时间戳），随后广播 |
| c→s | `image` | `{name, caption, dataBase64}` | 存 `images/`，向 `chat-in.md` 追加一行 `[图片 images/<file>] <caption>`，广播时带可访问 URL |
| s→c | `chat` | `{id,from,text,ts,image?}` | 新消息广播（用户消息、通讯官消息、系统消息共用） |
| s→c | `pending` | `{asks:[{askId,question}]}` | 待答集合变化时推送（watcher 监听 `outbox.md` 与 `outbox-replies.md`，做差集得出未闭环 ASK） |

**HTTP**（仅图片大图与备用轮询）：`GET /images/<room>/<file>`（带 CORS `*`）、`POST /upload`（备用，带 CORS）、`GET /poll`（备用）。

### 5.4 watcher 的四大职责（契约原文）在网络化后的映射

1. **搬运进**：WebSocket 收到用户消息 → 原样追加 `chat-in.md`（每条一段、带时间戳）。✅
2. **即时回**：追加成功后，立刻向**该房间所有连接**广播一条 `from:"system"` 消息："收到，马上转给开发主力"。注意契约要求这条不进 `chat-out.md`——广播但不落盘 `chat-out.md`（可落 `chat-in.md` 时间戳段内不必，直接 ephemeral 广播即可，但为让后到的设备也能看到"已收到"的体感，**允许**以 `system` 段落追加进 `chat-in.md`，因为它归 watcher 写）。
3. **唤醒**：见 §6.4。
4. **搬运出**：监听 `chat-out.md` 新增段落 → 广播到房间。

文件监听实现：用轮询兜底即可——每 1~2 秒比较各房间相关文件的 mtime/size 与已读偏移量，读出增量。这比 inotify 更可移植（macOS/手机沙箱都安全）。

## 6. 关键实现细节

### 6.1 消息解析（历史归并）

`chat-in.md` 段落由 watcher 写入，格式自控（建议：`## [U-<ts>] <ISO时间>` 起头，下接正文）；`chat-out.md` 段落由通讯官写入，格式同样以 `## [L-<ts>] <ISO时间>` 起头。**实施者需在 watcher 中同时提供"通讯官写入格式说明"，放进给通讯官的提示词补丁里**（见 §7），保证两头格式一致可解析。

### 6.2 房间创建

watcher 不主动建房。主 agent 开工时（liaison SKILL.md 第 2 步建 mailbox 时）创建 `rooms/<roomId>/` 并放入九文件模板。用户用不存在的房间号连接时，watcher 返回 `error:"房间不存在"`，网页提示人话："这个房间号不存在，问问 AI 是不是抄错了。"

### 6.3 安全

定位为个人自用工具，安全从简：房间号即凭证（知道地址+房间号即可进）。在文档和给用户的说明里注明"别把地址和房间号发给外人"。不实现 HTTPS/鉴权体系，但在代码中预留 `--token` 参数位。

### 6.4 唤醒通讯官（宿主适配点，最重要）

契约要求 watcher 叫醒通讯官。watcher 是独立 Python 进程，**无法直接调用宿主 agent 框架的 API**，按宿主能力二选一，实施时探测：

- **方案 A（首选，CodeBuddy 等支持文件监视的宿主）**：通讯官被 spawn 后，自身使用宿主的文件监视能力（如 Monitor 工具）盯住本房间的 `chat-in.md`、`outbox.md`、`status.md`，文件一变即被唤醒处理。watcher 不需要做任何叫醒动作，但**必须把这三个文件的变化做到"落盘即发生"**（写入后 flush）。
- **方案 B（宿主支持向运行中 agent 发消息）**：watcher 检测变化后写触发文件 `mailbox/rooms/<room>/.wake`，主 agent 侧的 Monitor 观察到此文件即向通讯官 SendMessage。
- 实现时在 `chat-watcher.py` 顶部常量 `WAKE_MODE = "none" | "signal-file"` 切换，默认 `none`（方案 A）。

### 6.5 DONE 检测

watcher 检测到某房间 `status.md` 出现单独一行 `DONE` 时，向该房间广播一条 `system` 消息："任务完成，总结马上来～"（最终总结由通讯官本人按契约发出，watcher 只烘托）。此后该房间继续可读，用户可回看历史。

## 7. 对 liaison 技能流程的适配说明（实施者同步要做的事）

实现这两个文件后，按 liaison `SKILL.md` 第 3 步接入时，主 agent 需要：

1. 启动 `chat-watcher.py`（后台常驻），记录地址与端口；
2. 创建房间目录、放入九文件模板，把 `<SKILL目录>/files/` 中的模板改为从 `rooms/<roomId>/` 读取；
3. 生成房间号（4 位数字，好念好记），连同 watcher 地址一起**用大白话告诉用户**，例如："开工啦。打开我给你的那个聊天网页，地址填 `http://123.45.67.89:8765`，房间号填 `8166`。"
4. 把成品 `chatroom.html` 通过当前对话的文件交付渠道发给用户（present_files / 工作区交付）；
5. spawn 通讯官时，在其指令中追加两段补丁：① chat 文件的段落写入格式（§6.1）；② 唤醒方式（§6.4 选定的方案）；
6. 若 AI 运行在远程沙箱而用户在本机/手机：由实施者负责解决网络可达（优先使用沙箱提供的公网访问入口/端口映射；必要时内网穿透），并把最终可访问地址给用户。**这是"即开即用"承诺的一部分，不能推给用户。**

## 8. 验收清单（全部通过才算完成）

- [ ] `chatroom.html` 双击打开（file:// 协议），无需任何安装；
- [ ] 首次填地址+房间号进入成功；关闭重开自动直连且历史完整；
- [ ] 手机浏览器（窄屏）下：输入框不遮挡、按钮可点、图片可拍照上传；
- [ ] 两台设备同时在线，一发两收；
- [ ] 用户发话 → 出现在 `chat-in.md`；通讯官写入 `chat-out.md` → 2 秒内出现在网页；
- [ ] 四个快捷按钮行为符合 §4.2（含「停！」二次确认、报bug三栏模板）；
- [ ] `outbox.md` 有未答复 ASK 时横幅置顶，答复落 `outbox-replies.md` 后横幅消失；
- [ ] 断网 10 秒恢复后自动重连，不丢消息；
- [ ] watcher 零 pip 依赖，`python3 chat-watcher.py` 一条命令启动；
- [ ] watcher 只写 `chat-in.md`（及 `images/`、`watcher.pid`、`.wake`），绝不写通讯官名下文件；
- [ ] 用户全程看到的文案无技术黑话。

## 9. 交付物

1. `chatroom.html`（单文件成品，可直接发用户使用）；
2. `chat-watcher.py`（单文件，放回 liaison 技能 `files/` 替换占位）；
3. 通讯官提示词补丁文本（§7 第 5 条）；
4. 一页给用户的图文使用说明（大白话，三张图：填地址、聊天、按按钮）。
